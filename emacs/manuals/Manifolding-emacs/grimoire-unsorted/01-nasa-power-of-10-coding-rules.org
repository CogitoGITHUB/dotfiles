* NASA Power of 10 Coding Rules
These rules were developed by NASA's Jet Propulsion Laboratory for safety-critical software. They emphasize simplicity, predictability, and verifiability.

** Rule 1: Avoid complex control flow
- Description: No `goto`, `setjmp`, `longjmp`, or recursion.
- Why: Simpler control flow is easier to reason about, verify, and test.
- Application: In Emacs Lisp or Org workflows, minimize nested calls, loops, and indirect jumps; prefer clear, linear sequences.

** Rule 2: Loops must have fixed upper bounds
- Description: Every loop should have a predictable maximum number of iterations.
- Why: Prevents infinite loops and ensures predictable behavior.
- Application: Document loop limits in scripts or Org Babel code; prefer mapping over iteration when possible.

** Rule 3: No dynamic memory after initialization
- Description: Avoid runtime heap allocation; use fixed memory or stack allocation.
- Why: Ensures deterministic memory usage; avoids fragmentation or runtime failures.
- Application: In Guix/Emacs, prefer static module definitions, fixed-size buffers, and preloaded configurations.

** Rule 4: Functions fit on one page (~60 lines)
- Description: Keep functions small and readable.
- Why: Easier to review, reduces hidden complexity, improves maintainability.
- Application: Treat Org headings or Babel blocks as “functions”; keep them concise.

** Rule 5: Use at least two asserts per function
- Description: Insert multiple assertions to check assumptions.
- Why: Catches invalid states early and documents invariants.
- Application: Include tests, validation checks, or sanity assertions in code blocks or configuration modules.

** Rule 6: Declare data with minimal scope
- Description: Avoid globals; keep variables local.
- Why: Reduces side effects and coupling; simplifies reasoning.
- Application: Use lexical scoping in Emacs Lisp, local let-bindings, or modular Org files with minimal exposure.

** Rule 7: Check all function return values and parameters
- Description: Validate inputs and handle outputs consistently.
- Why: Defensive programming prevents silent errors.
- Application: Always check function results in code blocks and scripts; handle errors explicitly.

** Rule 8: Limit the preprocessor to includes and simple macros
- Description: Avoid complex macros that hide logic.
- Why: Complex macros confuse humans and tools; obscure behavior.
- Application: In Lisp or Org, minimize meta-programming; prefer explicit code over macro-generated code.

** Rule 9: Limit pointer usage
- Description: Single level of indirection; avoid function pointers.
- Why: Multiple indirection layers complicate reasoning and debugging.
- Application: In higher-level languages, limit callbacks and closures; avoid convoluted references.

** Rule 10: Compile with all warnings enabled and fix them
- Description: Treat all compiler or interpreter warnings as errors.
- Why: Warnings often signal real bugs or risky code patterns.
- Application: In Emacs Lisp, Guile, or shell scripts, enable linting and static analysis; resolve all warnings.

** Notes
- These rules are strict for safety-critical systems but can be adapted to higher-level environments.
- They emphasize simplicity, modularity, and verifiability.
- For your Shapeshifter architecture, treat Org headings, modules, and Babel blocks as “functions” for rule application.
