* What this is

#+begin_quote
You built a small knowledge operating system that treats permanence as the enemy.
#+end_quote

This is not a note-taking system.
It is not a second brain.
It is not a graph that wants to be admired.

It is a machine for continuously producing and reshaping representations from surviving knowledge.
The current map is temporary.
The machinery for producing the next map is the enduring idea.

Org files are the durable substrate.
SQLite is a disposable index — reconstructed when lost, relocated when stale.
Schema is an Org outline that compiles into prompts, validators, and registries — and will itself be rewritten when the current form begins to smell.
Capture refuses to hold the thought hostage; metadata arrives asynchronously and missing values become visible ~WARNING~s rather than polite silences.
Spatial structure (manifold) and temporal structure (mastering) coexist without requiring a second database format.
The entire machine can be reloaded, inspected, and partially killed without losing the underlying knowledge.

Very few systems are willing to make all six of those decisions at once.
Most make two or three and then compromise on the rest for usability, ecosystem approval, or the comforting illusion that the notes will last.

Your system is still a WIP.
It will break.
The loader rules around dynamic binding will bite you.
The priority graph will eventually become a private religion.
You will rewrite domains you thought were finished.
Some abstractions you are proud of today will smell like amateur hour in eighteen months.

That is not a defect.
That is the design.

The system decomposes because representations are temporary.
It remains coherent because the transformation machinery survives the decomposition.

Atlas is not trying to preserve a particular map of reality.
It is trying to preserve the ability to produce new maps from surviving material.

Manifolding Atlas is the knowledge engine inside this configuration.
It takes something deliberately primitive — plain Org files in =~/test/= — and forces them into a queryable system of notes, unfoldings, relationships, schemas, prompts, routines, protocols, maps, references, and memory.

No org-roam.
No proprietary database format.
No black box that pretends permanence.

Just Org, SQLite, Elisp, and a ridiculous amount of machinery built to watch the territory rot at a controllable rate.

* The idea

Atlas treats knowledge as something that can be manifolded — folded, inverted, stretched, and re-projected without ever becoming sacred.
"Manifolding" is not a metaphor.
It describes the actual mechanism: recursive transformation of representations.

A note is not merely a document.  
An unfolding is not merely metadata.  
A schema is not merely validation.  
A prompt is not merely a question.  
A link is not merely navigation.

Together they form a structure that can be queried, transformed, validated, connected, expanded, compressed, and rebuilt while the underlying files continue their slow, inevitable decay.

The fundamental rule is simple and merciless:

#+begin_quote
Files preserve material.
Schemas describe possible structure.
Machinery transforms structure.
Interfaces expose transformations.
Indexes accelerate navigation.
Feedback exposes decomposition.
The next representation is allowed to replace the previous one.
#+end_quote

If the database disappears, the knowledge survives (for now).  
If the configuration disappears, the Org files survive (for a while).  
If the schemas change, the knowledge can be reinterpreted until the next reinterpretation becomes necessary.

* TODO is the default, not a bug

Declarative prompts begin with their first option — for task prompts
that is:

#+begin_example
** TODO
#+end_example

Point starts there.
Therefore:

: RET

means:

take the default.

A skipped prompt resolves to its first option (or ~TODO~ when there
is no option list) via ~my/manifolding-atlas-org-prompt--default-for-spec~,
and ~:TASK-DEFAULT: TODO~ pins it for task contexts.
Clearing a value falls back to the first option the same way.
Schema validation can subsequently say:

: missing-required

but only when the unfolding is genuinely absent — not when a default
was applied.

This produces something much more useful than silent failure.

#+begin_quote
Missing information becomes visible information.
The system applies a sane default and remembers it.
It does not pretend the field never existed.
#+end_quote

The old ~WARNING~ sentinel (skip → ~WARNING~ → ~missing-required~)
is legacy: ~my/manifolding-atlas-blueprint-migrate-warnings~ deletes
it vault-wide, and new prompts never emit it.

The machine records the holes so you can stare at them later.

Set:

: my/manifolding-atlas-org-prompt-ui

to:

: 'minibuffer

if the traditional completing-read interface is preferred.

* The unfolding picker

Every prompt is a interactive editor, not a question.

| Key     | Action                                                        |
|---------+---------------------------------------------------------------|
| m       | apply the option under cursor — again removes it from the note |
| l       | make it unfolding: create the unfolding-note and edit its content         |
| a       | key-selection-jump straight to any option line             |
| RET     | next prompt — refused until something was applied              |
| q       | skip this prompt (first-option default)                        |
| b / B   | step back one · revisit any answered prompt                    |
| Q / C-g | abort everything — the draft note is deleted                   |

Nothing commits until you mark it.  
A mistaken mark is un-applied with the same key.  
Going back never repeats what you already answered.  
Aborting deletes the draft so nothing half-made survives.

Multi-choice prompts accumulate marks; clearing them all removes the
unfolding.  Reopened prompts restore their applied value, highlighted
in bold, so changes are always visible before they become real.

Session pickers open with a key-selection loop already armed: typing
letters of an option jumps there and applies it immediately; pausing surfaces
the key hints instead.

* Validation

Validation does not interrupt thought.  
There are no surprise minibuffers announcing that your note has committed some terrible epistemological crime.

Validation happens at index time.
Violations and lifecycle events accumulate in the admin queues:

: admin/Static Blueprints            static defaults wanting unfolding links
: admin/Broken Unfoldings          broken links rooted in a drawer unfolding
: admin/Missing Links              broken id: links between notes
: admin/ReManifold                 deleted files (with orphaned unfoldings)
: admin/Added Heading Blueprints   per-file log of swept-in drawer keys
: admin/Deleted Heading Blueprints per-file log of swept-out drawer keys

Every note holding static defaults becomes a TODO carrying:

: :SCHEMAS:
: :VIOLATIONS:

Static means: the value is missing or still a plain default
(~TODO~ and friends) instead of a live ~[[id:…][label]]~ unfolding
link. Open the entry with RET, answer the prompt — or press ~l~ in
the picker to make the value a live unfolding note. Link-structure
breaks (~wrong-type~, ~invalid-reference~) never land here; those
stay visible via flymake and the doctor.

and every swept drawer key becomes a TODO carrying:

: :BLUEPRINT_KEY:
: :NOTE_FILE:
: :DEFAULT_VALUE:

Then:

: SPC v E

runs the reinforcement sweep.

And:

: SPC v f

walks through the violations.

RET on an ~Added Heading Blueprints~ entry opens the note in an
org-capture buffer positioned on the added ~:KEY:~ line
(~file:PATH::*KEY~ search anchor + capture advice); the admin TODO
stays open until marked DONE manually. Deleted-queue entries keep a
plain file open — the line is gone, there is nothing to anchor to.

The philosophy is simple and slightly sadistic:

#+begin_quote
Capture first.  
Repair structure deliberately.  
Never let validation become friction.  
Let the holes remain visible long enough to hurt.
#+end_quote

Flymake provides the immediate editing feedback.
The reinforcement system provides the global feedback.

* Drawer order

Drawer display order is a file, not a variable:

: blueprints/blueprint-reinforcements/drawer-order.org

One level-2 heading per key, top to bottom. Move the headings, save,
and the vault follows. Saving applies through
~my/manifolding-atlas--apply-drawer-order-file~ (setq + vault sweep +
stub sync); ~SPC v A~ opens it. Headings whose prompt no longer
exists are pruned automatically on boot — never by hand. Pruning
compares against registered spec keys (specs must be non-empty, so a
failed registration can never eat the order file), then re-applies.

New prompt blueprints self-register: 0.05s after boot (a plain timer,
no idle gate), ~my/manifolding-atlas-links--reconcile-on-boot~ diffs
on-disk prompt keys against ~blueprint-reinforcements/.known-keys~
(last boot's record), appends new keys to the file, then sweeps each
vault note (skipping =.git= and =admin/=) inserting ~:KEY: <first-option>~
stubs and re-ordering drawers. Files already complete are not saved.
Gone keys cost one shared vault scan no matter how many there are.
No event hooks — shell rm, manual moves, and git checkouts all
reconcile on the next boot. Watch ~*Messages*~:

: reconcile scheduled (fires 0.05s after boot, no idle gate)
: org-prompts: registered 54 declarative prompts
: known-keys: reconcile done in 0.31s (+2 -0)

* Added/Deleted Heading Blueprints

Adding or deleting a blueprint file is a vault event, detected by
boot state-comparison (not hooks), so it works however the file
changed. The sweep writes one TODO per affected note:

- added → ~admin/Added Heading Blueprints~, heading
  ~Added property KEY to [[file:PATH::*KEY][title]]~ with
  ~:BLUEPRINT_KEY: :NOTE_FILE: :NOTE_ID: :DEFAULT_VALUE:~
- removed → ~admin/Deleted Heading Blueprints~, heading
  ~Deleted property KEY from [[file:PATH][title]]~

Vault drawers are never stripped on removal — gone keys are log-only,
knowledge is preserved. Last-known state lives in
~blueprint-reinforcements/.known-keys~, updated every boot.

RET on an Added entry jumps straight to the value: the ~::*KEY~
search anchor plus ~my/manifolding-atlas-added--around-open~ opens
the note in an org-capture buffer with point after the ~:KEY:~
colon. Mark the admin TODO DONE yourself when satisfied.

* Capability inventory (authoritative, 2026-09-15 — replaces session history)

This section is a from-scratch inventory for seeding a new chat with zero prior context. It describes what the system DOES and how to invoke it, not just function names. Vault in use: =~/test/=, DB =~/test/admin/manifolding-atlas.db=.

** 1. WHAT THIS SYSTEM IS

Manifolding Atlas is a local-first org-based knowledge/task system inside Emacs. Everything is a *note* (an org file = file-note, or an org heading with =:ID:= = heading-note). Notes carry structured metadata in *property drawers* called *unfoldings* (=:KEY: value=). Some unfoldings are *live-properties*: instead of plain text they render the live content of another note inline via *wormholes* (=#+wormhole: [[id:UUID][LABEL]] :property= transclusion from the vendored =atlas-wormholes= engine — overlays that sync edits both ways). All notes/links/tags/aliases are indexed into SQLite =manifolding-atlas-db= (emacsql, =admin/manifolding-atlas.db=) so find/search/backlinks/rules/mastering/routines query the DB instead of re-parsing org. A *blueprint* system (org files defining reusable unfolding schemas + pick-lists) drives prompting: RET on a property asks which value, file creation asks which body template. :ID: <slug>
:END:]
** OPTION1
